# 02 · 架构设计

## 2.1 总体结构

```
┌─────────────────────────────────────────────────┐
│  浏览器（原生 ES6，零构建）                       │
│  库存数据 · 配料求解 · 参数设定                   │
└───────────────────────┬─────────────────────────┘
                        │ REST / JSON
┌───────────────────────┴─────────────────────────┐
│  FastAPI (app/main.py)                          │
│  路由 · Pydantic 校验 · 静态托管                  │
├─────────────┬──────────────┬────────────────────┤
│  data.py    │  store.py    │  solver.py         │
│  数据加载    │  配置持久化   │  MILP 求解  ★      │
│  清洗/查询   │  JSON 落盘   │  SciPy HiGHS       │
└──────┬──────┴──────┬───────┴────────────────────┘
       │             │
  ┌────┴─────┐  ┌────┴──────┐
  │ Excel /  │  │ limits    │
  │ parquet  │  │ .json     │
  └──────────┘  └───────────┘
```

## 2.2 技术选型

| 层 | 选型 | 理由 | 备选与否决原因 |
|---|---|---|---|
| 数据处理 | **Polars** | 4000 行是起步量，Polars 撑得住后续十万级；表达式 API 做清洗比 pandas 清晰 | pandas：数据量涨上来后要重写 |
| Excel 读取 | **fastexcel**（calamine） | Rust 实现，比 openpyxl 快一个量级；支持整表按字符串读入，是绕开混合类型坑的关键 | openpyxl：慢，且类型推断不可控 |
| 求解器 | **SciPy `milp`**（HiGHS） | 开源无 license；单订单毫秒级，多订单秒级，够用 | Gurobi/CPLEX：商业授权，本项目规模用不上；OR-Tools：多一个重依赖 |
| Web 框架 | **FastAPI** | 自带 OpenAPI 文档；Pydantic 校验省掉大量参数校验样板 | Flask：要手写校验和文档 |
| 前端 | **原生 ES6 + CSS 变量** | **零构建** —— 不需要 npm install，改完刷新即生效 | React/Vue：本项目复杂度用不上；且现场网络装 node_modules 很痛苦 |

### 关于「零构建」

这是一个有意识的取舍。三个页面、约 1000 行 JS，用框架带来的收益不足以抵消：

- 现场部署要能离线跑，`npm install` 拉几百个包不现实
- 工艺人员改一行提示文案，不该需要重新 build
- 没有构建产物，浏览器里看到的就是源码，排查问题直接

模块化靠原生 ES Module（`<script type="module">`），浏览器原生支持，无需打包。

## 2.3 模块职责

| 模块 | 职责 | 不负责 |
|---|---|---|
| `config.py` | 路径、参数定义、默认上下限。**唯一的配置真源** | 运行时状态 |
| `data.py` | Excel 读取、清洗、parquet 缓存、分页/排序/筛选查询、统计 | 业务规则判断 |
| `store.py` | 上下限与求解设置的读写、默认值合并、校验 | 使用这些配置 |
| `solver.py` | 候选池构造、可行性预检、MILP 建模求解、结果组装 | HTTP、持久化 |
| `models.py` | 请求/响应的 Pydantic 模型 | 业务逻辑 |
| `main.py` | 路由、异常到 HTTP 状态码的映射、静态托管 | 业务逻辑 |

依赖方向严格单向：`main → solver → {data, store, config}`，没有循环依赖。

## 2.4 数据流

### 启动

```
start.sh → uvicorn → app.main
                       ↓ 首个请求触发
                     data.get_inventory()
                       ↓ 缓存命中？
              ┌────────┴────────┐
           是 │                 │ 否
    读 parquet             读 Excel → 清洗 → 写 parquet
              └────────┬────────┘
                    内存缓存（进程级）
```

缓存是三层的：进程内存 → parquet 文件 → Excel 源。
点「重新导入」会穿透前两层重新读 Excel。

### 求解

```
前端收集订单 → POST /api/blend
                 ↓
            store.load()          读上下限配置
                 ↓
            build_pool()          等级过滤 + 缺失值过滤
                 ↓
            precheck()            可行性预检，无解直接返回原因
                 ↓
            候选预筛               每单取冻力最近的 N 批
                 ↓
            构造稀疏矩阵            scipy.sparse.coo_matrix
                 ↓
            milp() 求解            HiGHS
                 ↓
            组装结果               用料单 + 达成情况 + 共用批次
```

### 为什么用稀疏矩阵

约束矩阵规模约 `(K + K·J + n + 2P) × (2P + 1)`。4 单 × 200 候选时，
稠密矩阵是 `3600 × 1601 ≈ 576 万个浮点数`（44 MB），且绝大多数是 0。
用 `coo_matrix` 按非零元构造，内存占用降到几百 KB。

## 2.5 状态与并发

当前是**单机单用户**设计：

- 库存数据：进程内只读缓存，多请求并发安全
- 配置文件：`threading.Lock` 保护读写，但没有跨进程锁
- 求解：无共享状态，纯函数，并发安全

若要多用户部署，需要改动的点见 2.6。

## 2.6 扩展点

| 需求 | 改动位置 | 工作量 |
|---|---|---|
| 配置多套（按产线/客户） | `store.py` 的 `load/save` 加 profile 参数 | 小 |
| 配置存数据库 | 只改 `store.py` 的 `load/save`，其余代码不动 | 小 |
| 库存实时扣减 | `data.py` 增加已分配量字段，`solver.build_pool` 里扣减 | 中 |
| 方案留档与审批 | 新增 `history.py` + 数据表，`main.py` 加路由 | 中 |
| 多用户 + 权限 | FastAPI 中间件 + 会话，配置改数据库 | 中 |
| 对接 MES/ERP | `data.py` 的数据源从 Excel 换成 API/数据库 | 中 |
| 增加新的化验指标 | `config.PARAMS` 加一项 + `DEFAULT_LIMITS` 加一项 | **仅配置** |

最后一行值得强调：新增指标不需要改求解器、前端或接口。
`solver.py` 遍历的是 `limits` 里 `enabled` 的项，前端渲染的是 `/api/params` 返回的定义。

## 2.7 错误处理策略

| 场景 | 处理 | 理由 |
|---|---|---|
| parquet 缓存损坏 | 记警告，回退读 Excel 重建 | 缓存问题不该让服务起不来 |
| 配置文件损坏 | 记警告，回落默认值 | 同上 |
| 源 Excel 缺列 | 抛异常，附实际列名 | 这是真正的数据错误，必须暴露 |
| 目标超出可达区间 | 返回 200 + `status: INFEASIBLE` + 原因 | 这是**正常业务结果**不是 HTTP 错误，前端要展示原因而非报错 |
| 求解器内部异常 | 500 + 日志堆栈 | 程序缺陷，需要修 |

「无解」用 200 而非 4xx 是刻意的：客户规格配不出来是每天都会发生的正常情况，
前端需要把原因渲染成引导信息，而不是弹一个红色报错。
