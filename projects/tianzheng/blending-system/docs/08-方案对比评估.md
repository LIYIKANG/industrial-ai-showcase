# 08 · 方案对比评估

## 8.1 首先澄清：加权平均不是"算法"

混合后的指标**必然**是加权平均，这是物理规律，不存在"不用加权平均的求解方式"。
所以对比的两组不能是「加权平均 vs 新算法」。

真正能差异化的是**目标函数** —— 在同样的加权平均约束下，优化什么。
客户现在的做法本质是：*挑几批接近目标的料 → 手工算加权平均 → 校验是否达标*，
这是**贪心 + 校验**，不是优化。

| 对照组 | 实验组 |
|---|---|
| **贪心配料**（模拟人工）：按冻力接近度取料凑量，加权平均校验 | **MILP 全局最优**：同样的约束，但求全局最优，目标函数可选 |

对比的公平前提：**所有方案共用同一套加权平均约束、同一份客户规格、同一个候选池**，
只有目标函数不同。

## 8.2 五个参赛方案

| 代号 | 目标函数 | 业务含义 |
|---|---|---|
| `greedy` | 无（对照组） | 模拟人工试算 |
| `min_batch` | `min Σy` | 批次最少，省投料/清洗/转运工时 |
| `min_cost` | `min Σ xᵢ·单价(冻力ᵢ)` | 料本最低 |
| `min_redundancy` | `min Σ 超出规格的量` | 不白送品质 |
| `max_digest` | `min Σ 非难用料取用量` | 优先吃掉两端难出货的料 |

全部是**常数系数 × x** 的线性目标，所以求解难度不变。

## 8.3 实测结果

### 简单单：冻力 ≥210，3000 kg

| 方案 | 达标 | 料本 | 批次 | 消化难用料 | 耗时 |
|---|---|---|---|---|---|
| 贪心（对照组） | ✓ | ¥162,001 | 8 | 0 kg | 4 ms |
| 批次最少 | ✓ | ¥162,000 | **4** | 0 kg | 0.8 s |
| 料本最低 | ✓ | ¥162,000 | 4 | 0 kg | 1.5 s |
| 冗余最小 | ✓ | ¥162,000 | 4 | 0 kg | 1.5 s |
| 最大消化难用料 | ✓ | ¥183,973 | 5 | **3000 kg** | 1.5 s |

**人工在简单单上指标精度不差**（210.001 vs 210.000），差的是批次数（8 vs 4）。
不要拿"配得更准"去说服客户。

### 多指标单：冻力 ≥260±8 · PH ≤5.6±0.2 · 水分 ≤12±0.8，2000 kg

| 方案 | 达标 | 料本 | 批次 | 冗余 | 消化难用料 |
|---|---|---|---|---|---|
| 贪心（对照组） | **✗ 配不出** | ¥142,278 | 6 | 73% | 0 kg |
| 批次最少 | ✓ | ¥142,396 | **3** | 4% | 0 kg |
| 料本最低 | ✓ | **¥141,645** | 3 | 103% | 494 kg |
| 冗余最小 | ✓ | ¥142,406 | 3 | **2%** | 0 kg |
| 最大消化难用料 | ✓ | ¥148,345 | 4 | 6% | **2000 kg** |

贪心配出冻力 259.99（差 0.01）、PH 5.704（超标 0.104）—— **人工此时必须推倒重来**。
这才是新算法的卖点：**多指标规格下人工方法根本无法收敛**。

每个 MILP 方案都在自己的维度上拿第一，这正是"目标函数可选"的价值。

## 8.4 一个重要的数学事实：线性定价下料本没有自由度

```
料本 = Σ xᵢ · price(bloomᵢ)
```

若 `price` 对冻力**线性**，则

```
料本 = Σ xᵢ·(a + b·bloomᵢ) = a·W + b·(Σ xᵢ·bloomᵢ) = a·W + b·目标冻力·W
```

—— **完全由目标冻力决定，任何算法都省不出钱。**

只有价格曲线的**凸性**才带来优化空间：
- 凸（高冻力段涨价更快，本系统默认）→ 集中取料更便宜 → `min_cost ≈ min_batch`
- 凹 → 分散取料更便宜 → `min_cost ≈ max_digest`

**结论对客户很有价值**：单一冻力目标下，省钱的杠杆不在算法，而在
① 定价结构 ② 多指标带来的自由度 ③ 冻力冗余（配 213 而客户只要 210 就是白送）。

## 8.5 四项评估口径

### 成本 ⚠️ 占位数据

源表没有单价字段。当前用**冻力分档定价曲线**（断点 + 线性插值），页面可编辑。

> 默认价格是编的。**绝对金额只有相对比较意义，外发前必须换成真实价格。**

不用阶梯价的原因：阶梯价会让"配到 212 而客户只要 210"的冗余损失算成 0（同档内无差价），
而这恰恰是最想量化的东西。

### 指标冗余

方向敏感：`≥` 方向冗余 = 实际 − 要求；`≤` 方向 = 要求 − 实际；`±` 方向 = |实际 − 目标|。
统一用**占容差%** 归一。冻力那项额外折算成金额（`总量 × 单价差`）。

### 库存消化 ⚠️ 替代口径

**没有库龄数据** —— 源表原有 `月份` 列但整列是 `#REF!`（公式引用已断）。

替代口径：把冻力落在 p15（≤120.8）以下或 p90（≥274.7）以上的料定义为**难用料**，
这类料单独很难达标、必须靠混配出货，消化它们视为高价值。

**这不是真正的库存周转率。** 若能从原始台账恢复入库日期，这个维度可以立刻升级。

### 计算时间

墙钟时间，含建模开销。贪心毫秒级、MILP 秒级 —— **对业务无实质差别**
（人工试算一单要半小时）。展示时必须和方案质量并排，否则会误导。

## 8.6 权衡前沿（帕累托）

ε-约束法：先求批次数最优值 `k*`，再把 `max_batches` 从 `k*` 逐档放宽，每档求最低成本。

每个点的含义对业务方直白：**"最多用 N 批时，料本最低多少"**。
曲线越陡说明多用一批能省越多；走平说明再加批次已无收益。

> 单一冻力目标时前沿会退化成一个点（见 8.4，料本被钉死）。
> 多指标时才有真正的权衡曲线 —— 页面在只有一个点时会自动隐藏这一块。

## 8.7 开发中踩的坑

### 坑一：所有目标函数塌缩成 min_batch

初版把可选目标当**次级**目标（权重 40），而批次数是 100/批。
消化难用料要求低+高配对取料，批次数必然上升 3~4 批 = +300~400 惩罚，奖励最多 40 ——
求解器永远不会去做，表现就是「选了 `max_digest` 却消化 0 kg」，五个方案结果一模一样。

修正：**用户明确选定的目标必须是主目标**。优先级改为

```
选定目标 (≤5000)  ≫  批次数 (100/批)  ≫  居中 t (≤1)
```

`objective="min_batch"` 时该项恒为 0，退回原来的批次数优先，老行为不变。

### 坑二：难用料不在候选集里

修好权重后 `max_digest` 仍消化 0 kg —— 因为候选预筛只取目标附近的料，
难用料离目标很远，压根没进候选集，目标函数选不了不存在的变量。

### 坑三：单端注入 —— 同一个坑的第三次变体

把难用料按"离目标最近"注入后，消化量只有 377 kg（12.6%）。
原因：100 个名额被**离目标更近的那一端**（高端料）全部占满，没有低端料压秤，
加权平均立刻顶到容差上限 215，消化量被死死卡住。

修正：**两端各取一半**。修完消化量从 377 kg 涨到 3000 kg（100%）。

> 三次踩的是同一个坑：**任何按单一维度做的预筛/注入，都会在多维约束下偏向一端**。
> 距离维度漏掉矫正料、容量维度漏掉总量、单端注入漏掉压秤料。
> 凡是预筛，都要问一句「它会不会把本来可行的解筛掉」。

### 坑四：不达标的方案在维度上拿了第一

初版记分卡给贪心的"计算耗时 335 ms"标了绿框最优 —— 但贪心**根本没配出合格品**。
配不出合格品的方案再快再便宜也不算赢。

修正：**只在达标的方案里评最优**，未达标方案在维度对比里名字后加 ✗。

## 8.8 页面使用

「方案对比」页，第四个 tab。

1. 填客户需求（与配料页同构的目标指标组件）
2. 勾选参赛方案（默认全选）
3. 需要的话改定价曲线
4. 点「开始对比」

结果包含：评估记分卡（最优高亮 + 相对对照组增减）、各维度对比条、权衡前沿、
库存影响（各方案啃掉了哪一段）、指标冗余明细、用料单对照、CSV 导出。
